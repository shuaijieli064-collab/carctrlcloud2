## TL;DR

本文档是《全场景智能寻检车 APP 开发实战》微课项目的完整开发计划。本期核心目标：在没有真车的情况下，以 **TCP 直连模拟** 方式跑通"鸿蒙 APP（客户端）↔ PC 模拟小车（服务端）"的完整控制闭环，覆盖课程前三个模块（操控页 UI、摇杆组件、TCP 通信）；华为云物联网平台集成作为后期扩展列入路线图。文档遵循"背景阐述 → 资源盘点 → 带着问题和方向推进"的叙事主线，给出总体架构、8 个阶段的开发计划、关键技术方案、测试验收方案与风险应对。

## 1 项目背景

### 1.1 课程与项目定位

《全场景智能寻检车 APP 开发实战》是一门聚焦智能设备 APP 开发的微课程，围绕一台智能寻检车的手机端操控应用展开，包含四大技术模块：

| 模块 | 内容 | 本期范围 |
|------|------|---------|
| 模块① | 操控页面 UI 设计与实现（常用 UI 组件、样式定制、触摸事件） | 本期实施 |
| 模块② | 摇杆设计与开发（组件剖析、交互逻辑、集成实验） | 本期实施 |
| 模块③ | TCP 网络通信（原理、实现方法、通信功能测试） | 本期实施 |
| 模块④ | 华为云物联网平台集成（基础操作、协议解析、平台与车端交互） | 后期计划 |

### 1.2 问题背景：真车未到位，如何先行开发

寻检车 APP 的最终形态是"手机 APP 通过网络控制真车"。但在课程第一阶段，真车硬件尚未到位。若等真车到手才开始开发，UI、通信协议、联调问题会全部堆积到后期。解决方案是老师第一阶段指示的**模拟小车**思路：在 PC 上运行一个 Python 编写的模拟车端服务程序，持续监听固定端口，代替真车接受 APP 连接——这样 APP 侧的全部开发（UI、摇杆、通信、协议）都可以先行开展，后期仅需把"模拟车端"替换为"真车车端"，APP 代码几乎无需改动。

### 1.3 本期目标与范围界定

- **目标**：跑通"鸿蒙 APP（DevEco 模拟器）↔ PC 模拟小车"的 TCP 直连闭环：APP 发出摇杆控制指令，模拟车端回送指令回执与状态流，APP 页面实时呈现连接状态与小车状态。
- **范围内**：工程配置、操控页 UI、摇杆组件、TCP 客户端与指令协议、Python 模拟车端（car_server.py）、打桩联调（test_client.py）。
- **范围外（列入后期计划）**：浏览器俯视图深度开发、华为云 IoTDA 平台集成、真车替换。

### 1.4 老师第一阶段架构指示

老师给出的 TCP 直连实验方式包含四个角色与两条关键约定：

- **鸿蒙 APP**：TCP 客户端，运行在 DevEco 手机模拟器中；
- **模拟小车 car_server.py**：TCP 服务端，监听 8888 端口，在 PC 上运行、代替真车；
- **test_client.py**：开发期的"替身演员"，站在 APP 的位置打桩，先测车端；
- **浏览器俯视图**（后期扩展）：经 WebSocket 8889 只读观看小车运行，"只看不控"。
- **约定一**：连接永远由 APP 主动发起，`connect(小车IP, 8888)`，以长连接形式维持；
- **约定二**：模拟器环境中 `10.0.2.2` 等价于宿主机（PC）本机——APP 连接的是它，而不是 `127.0.0.1`。

### 4.2 TCP 连接与通信时序

![图2 TCP连接与通信时序](images/fig2_seq.png)

时序要点：连接建立后进入长连接双向模式；APP 每 5 秒发送心跳，15 秒未收到任何下行即判定断线并进入指数退避重连（1s→2s→4s→…上限 30s）；断线期间摇杆指令静默丢弃并保持急停状态，重连成功后自动恢复状态流。

## 6 关键技术方案

### 6.1 指令协议设计（JSON 文本帧 + `\n` 分帧）

TCP 是字节流，必须自行分帧。选择"JSON 文本帧 + 换行符分隔"：教学项目可读性高、ArkTS 与 Python 双端解析零成本、便于 test_client 手工调试。二进制定长帧（帧头+长度+CRC）性能更好但调试成本高，本期不采用。

**APP → 车端（指令）**：

```json
{"type":"move","seq":12,"lx":0.50,"ly":-1.00,"ts":1760000000000}
{"type":"stop","seq":13}
{"type":"ping","seq":14}
```

**车端 → APP（回执/状态）**：

```json
{"type":"ack","seq":12,"ok":true}
{"type":"state","speed":0.60,"battery":87,"heading":90,"x":1.2,"y":3.4}
```

协议约束：字段全小写；`seq` 单调递增用于回执匹配；`ly` 取负值为前进（与摇杆屏幕坐标系一致）。

### 6.3 长连接保活与重连

- APP 每 5s 发 `ping`；15s 未收到任何下行判定断线；
- 重连采用指数退避：1s→2s→4s→…→上限 30s；页面显示连接状态与重试次数；
- 断线期间摇杆指令静默丢弃并保持急停状态，避免"假操控"；
- 车端对应：收到 ping 回 pong；读超时主动清理连接。

### 6.4 ArkTS TCPSocket（`@ohos.net.socket`）使用要点

- `socket.constructTCPSocketInstance()` 创建实例；**connect 前必须先 `bind()`**（API 22 下不 bind 部分版本报 2301025 错误，高频坑）；
- `connect({address:{address:'10.0.2.2', port:8888}, timeout:5000})`；`extraOptions` 建议 `keepAlive:true`、`noDelay:true`；
- `on('message')` 回调中数据为 `ArrayBuffer`，用 `TextDecoder`（UTF-8）转字符串后按 `\n` 切帧、`JSON.parse`；发送用 `TextEncoder` 编码；
- 必须监听 `on('close')`/`on('error')`，统一进入重连状态机；页面销毁（`aboutToDisappear`）中 `close()` 释放，防止泄漏与重复连接；
- 网络回调非 UI 线程上下文，状态更新收敛到单一 ViewModel，避免并发刷新问题。

### 6.5 模拟器网络要点

- 模拟器内 `127.0.0.1` 指模拟器自身，**不是 PC**；连宿主机必须用 `10.0.2.2`；
- car_server 必须监听 `0.0.0.0` 而非 `127.0.0.1`，否则模拟器无法连入；
- IP/端口做成页面可配置并持久化（默认 `10.0.2.2:8888`），后期换真机测真车只需改 IP、不改代码；
- Windows 防火墙可能拦截 8888/8889 入站——联调排障清单中首查。

### 7.2 打桩测试用例（test_client.py）

| 用例 | 输入 | 预期 |
|------|------|------|
| 正常指令 | `{"type":"move","seq":1,"lx":0.5,"ly":-1.0}` | ack(ok=true) 且 state 中 speed 变化 |
| 急停指令 | `{"type":"stop","seq":2}` | ack(ok=true) 且 speed 归零 |
| 非法 JSON | `hello world` | 不崩溃，回错误提示或静默丢弃 |
| 缺字段指令 | `{"type":"move"}` | 拒绝并回错误说明 |
| 心跳 | `{"type":"ping","seq":3}` | 回 pong |
| 长连接稳定性 | 保持连接 5 分钟 | 持续收到 state 流，无中断 |

### 7.3 APP↔车端联调用例

- 正常操控：拖动摇杆，观察服务端指令流与 APP 状态面板刷新；
- 回执校验：核对 ack.seq 与下发指令 seq 一致；
- 断网重连：关闭 car_server 再重启，观察 APP 进入重连并自动恢复；
- 异常容错：车端发送半帧/超长报文，APP 不崩溃。

## 8 风险与应对

| 风险 | 等级 | 影响 | 应对 |
|------|------|------|------|
| 模拟器网络不通（10.0.2.2 不生效/防火墙拦截） | 高 | 完全无法联调 | 服务端监听 0.0.0.0；防火墙放行 8888/8889；先用 test_client 在本机 127.0.0.1 自测隔离问题 |
| TCP 粘包/拆包导致解析错乱 | 高 | 指令解析失败 | 统一 `\n` 分帧；双端复用同一分帧逻辑；用非法报文用例回归 |
| 网络回调线程刷新 UI 崩溃 | 中 | 页面异常 | 状态更新收敛到 ViewModel，UI 只读 @State |
| 连接泄漏/重复连接 | 中 | 端口耗尽、指令错乱 | aboutToDisappear 释放；连接前先关闭旧实例 |
| JSON 手写拼写错误 | 低 | 联调排查耗时 | 协议字段集中在 CommandProtocol/README 维护，双端对照 |
| 后期 MQTT 依赖缺失 | 低 | 阶段7受阻 | 后期评估引入三方库或基于 TLS Socket 自实现 |
